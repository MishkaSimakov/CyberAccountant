# Дизайн системы

## Сущности

Алгоритм выделяет в каждом документе сущности. Примерный вариант разметки показан ниже.

```
## Ведомость

РАСЧЕТНАЯ ВЕДОМОСТЬ ПО ОПЛАТЕ ТРУДА

Документ: <entity type="id" value="ВЕД-ЗП-2026-02" unit="string" id="143">ВЕД-ЗП-2026-02</entity>

Проект: <entity type="id" value="24/03/15-01" unit="string" id="144">24/03/15-01</entity> | Период: <entity type="date" value="2026-02" unit="date" id="145">Февраль 2026</entity>

| Код статьи | Вид начисления | Сумма, руб. | Основание |
| --- | --- | --- | --- |
| <entity type="id" value="0201" unit="string" id="146">0201</entity> | Основная заработная плата | <entity type="number" value="1015500.00" unit="rubles" id="147">1 015 500,00</entity> | Табель и расчет начислений |
| <entity type="id" value="0202" unit="string" id="148">0202</entity> | Дополнительная заработная плата и резерв отпусков | <entity type="number" value="101500.00" unit="rubles" id="149">101 500,00</entity> | Доплаты и компенсационные начисления |
|  | ИТОГО | <entity type="number" value="1117000.00" unit="rubles" id="150">1 117 000,00</entity> |  |
```

Виды сущностей:

- type="id" value="<string value>" unit="string" id="<unique number>"
- type="date" value="<date in standard form>" unit="date" id="<unique number>"
- type="number" value="<number in standard form>" unit="<rubles/euros/kg>" id="<unique number>"

## Требования

По первичным файлам и итоговому отчёту алгоритм составляет список требований. Он представляет собой JSON. Требования
бывают двух видов:

1. Формула - выражение, содержащее только id сущностей, константы и математические операции из ограниченного списка.
   Проверяется автоматическим верификатором.
2. Текстовое условие от LLM - она сама его составляет и проверяет. Нужно, когда выразительной способности формул не
   хватает.

Примерный вид JSON (может меняться):

```json
[
  {
    "equation": "#123 * 2 == #321"
  },
  {
    "equation": "#999 == \"ВЕД-ЗП-2026-02\""
  },
  {
    "equation": "01.01.2026 < #777 && #777 < 31.05.2026"
  },
  {
    "equation": "#1 + #2 == #3"
  },
  {
    "evidence": "Число #541 выглядит очень странно: зарплата больше чем 1e9.",
    "ids_related": [
      541,
      9654
    ],
    "verdict": "false"
  }
]
```

Требования могут поступать из разных источников. Например, LLM или алгоритм для данного типа столбца.

## Путь пользователя на фронтенде

Бухгалтер заходит на фронтенд. Видит список отчётностей. Каждая отчётность содержит в себе документы, результаты их
проверок и комментарии. Можно создавать новые отчётности и просматривать старые.

### Загрузка файлов

При создании отчётности открывается её страница, где можно загружать файлы. Файлы загружаются асинхронно. Производится
обработка с помощью OCR на стороне сервера. Клиент узнаёт о результатах через polling. Отображается текущий статус
каждого файла: загружается, загружен, обрабатывается, ошибка, обработан. Если файл обработан, то можно просмотреть
markdown-файл, полученный при его обработке. Его можно отредактировать. При этом в базе данных сохраняются версии файла.

При редактировании markdown-файла должна быть возможность смотреть side-by-side оригинальный документ и сгенерированный
markdown-файл.

Если при загрузке файла произошла ошибка, то её надо явно обработать, удалив файл. После этого его можно загрузить ещё
раз. При этом отображается конкретная ошибка.

Когда все файлы загружены и нет ошибок, становится активна кнопка перехода на следующую стадию.

### Разметка сущностей

На сервере на каждом файле параллельно запускается алгоритм, который выделяет в нём ключевые сущности: даты, числа,
идентификаторы. Сущности размечены, как XML-теги <entity> с параметрами вокруг конкретного фрагмента markdown-файла.
Аналогично отображаются состояния файла: обработан, ошибка. Если файл обработан, то можно просмотреть отмеченные
сущности и отредактировать их параметры. При сохранении добавляется новая версия. В интерфейсе версии пока что не
отображаются. Только показывается, что файл был отредактирован пользователем.

Когда все файлы размечены, становится активна кнопка перехода на следующий этап.

### Выделение и проверка требований

По сущностям и файлам модель выделяет требования к отчётности. Пока это происходит, пользователь видит загрузку.
Работает простой polling. Когда требования выделены и проверены, показывается отчёт. В нём можно посмотреть все
требования, увидеть только нарушенные. Требования можно редактировать. При этом создаётся новая версия и перепроверяется
на сервере. При нажатии на сущности в требовании можно посмотреть, из какого документа они пришли.

К требованиям можно оставлять комментарии. Если требование составлено на естественном языке и проверено моделью, то
должна быть возможность его заглушить. То есть отметить, что на самом деле нарушения нет. Требование при этом остаётся.

## База данных

### reports

- id
- name
- contract_number
- period_start
- period_end
- target_row
- stage
- processing_status
- timestamps

### files

- id
- name
- path
- hash
- markdown_path
- entities_path
- version
- report_id
- role - final or supporting
- status
- error
- size
- content_type
- timestamps

### requirements

- id
- report_id
- json
- note
- is_silenced

### entity file

Эта таблица полезна, когда надо вернуть пользователю то, из какого файла пришёл каждый из entity. Иначе надо будет
загружать все файлы и заново их парсить.

- report_id, entity_id - combined primary key
- file_id
