# Локальное преобразование документов в Markdown с координатами

Конвертер `document-ocr` принимает путь к исходному файлу и путь к выходному Markdown.
Поддерживаются PDF с текстом, PDF-сканы, PNG/JPEG/TIFF/BMP/WebP, DOCX, XLSX,
TXT и MD. Документы обрабатываются локально, без вызовов LLM. DOCX/XLSX передаются
по HTTP сервису `office_sandbox` внутри локальной сети Compose. Загрузчик сайта
принимает PDF, DOCX, XLSX, PNG и JPEG; остальные форматы доступны через CLI.

## Запуск приложения и параллельная обработка

Из корня репозитория, с установленными Python 3.13+ и работающим Docker Compose
с Linux-контейнерами:

```powershell
# Запуск с одним Office- и одним OCR-воркером по умолчанию.
python scripts/start.py

# Два одновременных Office-задания и три процесса обработки документов.
python scripts/start.py --office-workers 2 --ocr-workers 3

# Режим разработки с Vite и перезагрузкой исходников.
python scripts/start.py --dev --office-workers 2 --ocr-workers 3

python scripts/start.py --help
```

Обычный режим открывает сайт на http://localhost:8000, режим `--dev` — на
http://localhost:5173. Создайте отчёт на сайте и загрузите исходные документы:
они автоматически попадут в очередь OCR. Зависимости Python, Tesseract с языками
`rus`/`eng` и LibreOffice устанавливаются при сборке контейнеров. На хосте для
этого запуска не нужны pip-пакеты проекта. Если Docker не найден, скрипт пытается
использовать Podman Compose.

| Параметр | Что передавать | Что регулирует |
| --- | --- | --- |
| `--office-workers N` | Целое число больше нуля | Максимум одновременных конвертаций DOCX/XLSX в Office-песочнице |
| `--ocr-workers N` | Целое число больше нуля | Количество RQ-процессов, каждый обрабатывает один документ за раз |
| `--dev` | Флаг без значения | Запуск `compose.dev.yaml` вместо `compose.yaml` |

Без явных настроек оба числа равны **1**. Можно передать только один параметр.
Настройки также читаются из `OFFICE_WORKERS` / `OCR_WORKERS` в `.env` или окружении
терминала. Приоритет: **параметр CLI → окружение терминала → `.env` → 1**.
Например, в `.env`:

```dotenv
OFFICE_WORKERS=2
OCR_WORKERS=3
```

Скрипт сохраняет существующий `.env`, а при его отсутствии создаёт пустой файл.
Далее выполняет `compose up -d --build`: собирает образы, использует кэш сборки
и создаёт либо обновляет контейнеры. Названия проектов — `cyberaccountant` и
`cyberaccountant-dev`; их можно переопределить через `COMPOSE_PROJECT_NAME`.
Повторный запуск с другими числами меняет конфигурацию воркеров. Менять её лучше
после завершения текущей обработки, чтобы не прерывать задания.

Команда запуска **не принимает пути к документам**, не загружает файлы и не
перезапускает OCR уже обработанных документов. Она завершается после запуска
контейнеров; окончания обработки очереди нужно дождаться на сайте. Для сравнения
производительности загружайте тот же набор в новый отчёт после запуска окружения.

### Как работают два лимита

Каждый OCR-процесс берёт файл из общей Redis/RQ-очереди. Для DOCX/XLSX он сначала
ждёт результат Office-сервиса, затем строит Markdown и координаты символов.
PDF и изображения обрабатываются без Office. Разные файлы могут одновременно
находиться на разных стадиях; порядок действий внутри одного файла сохраняется.
Пул извлечения сущностей и проверки ограничений эти параметры не меняют.

Office-сервис допускает не более `OFFICE_WORKERS` конвертаций одновременно;
каждая выполняется в отдельном процессе с собственной временной папкой, профилем
LibreOffice, домашним каталогом и уникальным UNO-каналом. Остальные запросы ждут
свободного места до 180 секунд. На саму конвертацию отведено ещё до 180 секунд.
Клиент учитывает оба интервала. Для одного приложения с `OCR_WORKERS=1` увеличение
только `OFFICE_WORKERS` не даст параллельной обработки файлов.

По умолчанию выбран один воркер для экономии памяти. Лимиты Office-контейнера
общие для всех его процессов: 2 CPU, 1 ГиБ RAM, 128 PID и ограниченный tmpfs.
Большее число воркеров не увеличивает эти ресурсы автоматически и не гарантирует
пропорционального ускорения. Практическая начальная настройка — 2/2; затем
сравнивайте время полной обработки вашего набора и расход памяти.


В режиме разработки используйте `docker compose -p cyberaccountant-dev -f
compose.dev.yaml` вместо `docker compose -p cyberaccountant`. Остановка без
`--volumes` сохраняет документы и базу в именованных томах. Перед переключением
между обычным режимом и `--dev` остановите предыдущий: оба используют порт 8000.

## CLI для одного документа

Для использования конвертера вне контейнера установите пакет сервера и Tesseract.
На Debian/Ubuntu, из корня репозитория:

```bash
sudo apt install tesseract-ocr tesseract-ocr-rus fonts-dejavu-core
python -m pip install -e ./server
python -m server.app.ocr --help
```

На Windows установите Tesseract с языками `rus` и `eng` отдельно и добавьте его
в PATH либо передайте `--tesseract` и `--tessdata`. Команды `document-ocr` и
`python -m server.app.ocr` вызывают один конвертер; второй вариант выполняйте из
корня репозитория. Офисный движок используется только через локальный сервис.

Для DOCX/XLSX удобнее вызвать CLI внутри уже запущенного контейнера, где доступны
и Tesseract, и Office-сервис. Пример в PowerShell с существующим `input.xlsx`:

```powershell
python scripts/start.py
docker compose -p cyberaccountant cp "./input.xlsx" server:/tmp/input.xlsx
docker compose -p cyberaccountant exec server document-ocr /tmp/input.xlsx /tmp/ocr-result/result.md
New-Item -ItemType Directory -Force "./output" | Out-Null
docker compose -p cyberaccountant cp server:/tmp/ocr-result ./output/result
```

Результаты окажутся в `output/result/`: Markdown, JSON с координатами и каталог
`result.assets/`. Пути в команде `exec` относятся к контейнеру, поэтому исходник
сначала копируется туда, а результаты — обратно. Этот разовый вызов CLI обрабатывает
один файл и не использует RQ-пул. Параметры `--office-workers`/`--ocr-workers`
принимает запуск приложения, а не конвертер одного файла.

### Пересчёт формул и изоляция

Для XLSX порядок обработки обязателен:

1. Копия файла поступает в песочницу; исходник доступен только для чтения.
2. OOXML проверяется на макросы, OLE/ActiveX, внешние источники данных и опасные
   формулы (`DDE`, `WEBSERVICE`, `CALL`, `RTD` и другие).
3. LibreOffice загружает книгу с `MacroExecutionMode=NEVER_EXECUTE` и
   `UpdateDocMode=NO_UPDATE`.
4. Вызывается **`calculateAll()`**, даже при ручном режиме расчёта или старом кэше `0`.
5. Проверяются ошибки формул; сохраняется `recalculated.xlsx` с новым кэшем.
6. Из этого же состояния книги экспортируется PDF, затем строятся Markdown и bbox.

Пересчитываются формулы листов, включая зависимости между ячейками и листами.
Макросы, скрипты, DDE-команды и встроенные программы не запускаются.
DOCX проходит в той же песочнице экспорт в PDF с отключёнными макросами.

Office-контейнер подключён только к внутренней сети Compose и работает от
пользователя `10001:10001`, без Linux capabilities и повышения привилегий,
с read-only корнем. Есть лимиты
1 ГиБ RAM, 2 CPU, 128 PID и времени конвертации (180 секунд).
Профиль LibreOffice и рабочие файлы находятся в ограниченных временных tmpfs.
Входной файл передаётся в теле локального HTTP-запроса. Домашний каталог хоста,
проект и Docker socket офисному контейнеру не монтируются. Результат возвращается
как TAR по HTTP, размер ограничен; архив разбирается без `extractall`, ссылки
и посторонние имена запрещены. По таймауту завершается группа процессов задания.

При ошибке/неподдерживаемой формуле, неполном пересчёте, отсутствии нового кэша
или недоступной песочнице обработка останавливается. Старое значение не подставляется
и не заменяется нулём. Функции Excel и Calc могут отличаться; полный паритет со
всеми Excel-функциями не гарантируется. Формулы с внешними источниками не поддерживаются.

Изоляция относится к этапу офисного движка; чтение PDF и OCR выполняются в
OCR-воркере (либо в процессе CLI при разовом вызове). Контейнер ограничивает последствия обработки документа,
но не является доказательством отсутствия уязвимостей в ядре/движке контейнеров.

## Запуск

После локальной установки пакета, из корня репозитория:

```powershell
python -m server.app.ocr "данные/01_Карточка_учета_фактических_затрат_этап_3.pdf" "output/kfz.md"
python -m server.app.ocr "данные/12_Акт_связь_0426.png" "output/communication.md"
```

| Аргумент конвертера | Значение |
| --- | --- |
| `input` | Обязательный путь к исходному файлу |
| `output` | Обязательный путь к выходному `.md` |
| `--boxes PATH` | Другой путь к JSON координат; по умолчанию рядом с Markdown, с суффиксом `.boxes.json` |
| `--ocr auto\|always\|never` | Автоматический выбор OCR, принудительное распознавание или чтение только текстового слоя; по умолчанию `auto` |
| `--lang LANG` | Языки Tesseract; по умолчанию `rus+eng` |
| `--dpi N` | Разрешение рендеринга PDF для OCR, от 72 до 600; по умолчанию 300 |
| `--psm MODE` | Режим сегментации Tesseract; по умолчанию `auto` |
| `--timeout SECONDS` | Таймаут внешних вызовов конвертера; по умолчанию 180 секунд, Office-клиент дополнительно учитывает ожидание свободного слота |
| `--office-url URL` | Адрес локального Office-сервиса; по умолчанию `OFFICE_SANDBOX_URL` или `http://office_sandbox:8001` внутри Compose |
| `--no-cell-ocr` | Пропустить дополнительное распознавание отдельных ячеек сканов |
| `--no-tables` | Отключить восстановление таблиц |

DOCX/XLSX требуют доступного Office-сервиса; для них используйте пример CLI
внутри контейнера из предыдущего раздела. Все параметры перечислены в
`python -m server.app.ocr --help`.

Пути могут содержать пробелы и кириллицу. Каталоги создаются автоматически.
Пример явных настроек:

```powershell
python -m server.app.ocr "input.pdf" "output/result.md" --boxes "output/geometry.json" --lang rus+eng --dpi 400
```

Результаты для `output/kfz.md`:

```text
output/
  kfz.md                  Markdown, UTF-8
  kfz.boxes.json          символы, нормализованные координаты и позиции в Markdown
  kfz.assets/
    preview.pdf           фиксированное отображение для подсветки
    page-0001.png          точное изображение страницы без OCR-разметки
    recalculated.xlsx      для XLSX: копия с пересчитанными формулами и кэшем
    office-report.json     для Office: старый кэш, результаты формул, настройки изоляции
```

При повторном запуске артефакты с тем же именем перезаписываются. Исходник
не изменяется. Папка `.assets` выделена для результатов этой конвертации;
если страниц стало меньше, старые PNG могут остаться, актуальные перечислены
только в JSON.

## Что означает bounding box

**PDF:** координаты связаны с видимой страницей исходного PDF с учётом её
поворота и CropBox. `preview.pdf` — копия исходника. Единица — PDF point (1/72 дюйма).
Встроенные текстовые фрагменты дают координаты из PDF; сканы — из Tesseract.

**Изображения:** координаты в пикселях изображения после применения EXIF-поворота.
Один пиксель соответствует одной единице страницы preview.pdf. Исходное
разрешение сохраняется, изображение не увеличивается до 300 DPI.
Для изображения с EXIF-поворотом нужны либо обычный просмотрщик, учитывающий EXIF,
либо предоставленное preview; сырые координаты до EXIF-поворота будут другими.

**DOCX/XLSX/TXT/MD:** у файла нет единственной фиксированной геометрии страниц.
Скрипт сначала создаёт `preview.pdf`, затем получает настоящие координаты символов
в этом отображении. Для подсветки нужно показывать этот PDF или его PNG.
Координаты не следует переносить в произвольно открытый Word/Excel: шрифты,
масштаб и переносы могут отличаться. Адреса исходных XLSX-ячеек и DOCX-абзацев
в текущей версии отдельно не экспортируются.

Во всех случаях:

- начало координат — левый верхний угол видимой страницы;
- X направлен вправо, Y вниз;
- `bbox_normalized = [x0 / width, y0 / height, x1 / width, y1 / height]`;
- номер страницы начинается с 1;
- сохраняются только нормализованные координаты отдельных символов, без боксов слов и таблиц;
- для PNG-превью: `x_px = x_normalized * page.image_width`, аналогично Y.

На сканах bbox — оценка OCR-движка, а не гарантия идеально точного контура буквы.
Скрипт не делит прямоугольник слова на равные части для имитации координат символов.

## JSON и связь с Markdown

В схеме `2.0` массив `characters` плоский: одна запись на один Unicode code point.
Записей слов и вложенных списков символов нет:

```json
{
  "id": "p1-c42",
  "text": "6",
  "markdown_span": [710, 711],
  "page": 1,
  "bbox_normalized": [0.706, 0.368, 0.720, 0.382]
}
```

Числа в примере условные. Для PDF это геометрия символов из PDF, для OCR —
результат Tesseract box output. Координаты ограничены видимой страницей и
нормализованы без дополнительного округления. Для восстановления абсолютных
координат умножьте X на `pages[page - 1].width`, Y — на `.height`.

Если один глиф содержит несколько code points (например, лигатура), они
экспортируются отдельно с одинаковой реальной областью глифа. При расхождении
символьного и словного распознавания сопоставляются совпадающие части текста;
у несопоставленного глифа `markdown_span = null`. Для символов текста без
видимого глифа координаты не придумываются: их количество записывается в
`pages[].unmapped_character_count` и сопровождается предупреждением.

`markdown_span` — полуинтервал `[start, end)` в **Unicode code points**, не байтах:

```python
fragment = markdown[start:end]
assert fragment in (character["text"], "\\" + character["text"])
```

Если текстовый объект PDF частично выходит за видимую страницу, символьные
координаты обрезаются по границе страницы и добавляется предупреждение.
Исходные необрезанные координаты отдельно не сохраняются.

Спецсимволы Markdown экранируются: например, у символа `|` диапазон указывает
на два символа Markdown `\|`. Добавленные разделители таблиц, HTML `<br>` и
пробелы между словами не имеют координат. У суммы `650 000,00` есть девять
записей цифр и запятой; диапазон всей суммы выбирает их независимо от границ слов.

В JavaScript для тех же смещений используйте `Array.from(markdown).slice(start, end).join('')`:
обычный `String.slice` считает UTF-16 units и отличается на emoji и других символах вне BMP.
После редактирования Markdown координатный индекс нужно строить заново;
SHA-256 исходника и Markdown сохранены в JSON.

## Подсветка найденной ошибки

Выбрать символы по диапазону Markdown в Python:

```python
import json
from pathlib import Path
from server.app.ocr.converter import characters_for_span, highlight

boxes = Path("output/kfz.boxes.json")
data = json.loads(boxes.read_text(encoding="utf-8"))
md = Path("output/kfz.md").read_text(encoding="utf-8")
start = md.index("1 145 798,10")
ids = characters_for_span(data, start, start + len("1 145 798,10"))
highlight(boxes, ids, Path("output/error.pdf"))
```

Или через CLI, указав идентификаторы из JSON:

```powershell
python -m server.app.ocr highlight "output/kfz.boxes.json" "output/error.pdf" --characters p1-c42 p1-c43
```

Либо по смещениям (подставьте реальные значения):

```powershell
python -m server.app.ocr highlight "output/kfz.boxes.json" "output/error.pdf" --span 710 725
```

Диапазонная подсветка проверяет хеш Markdown и отказывается использовать
устаревшие позиции. Подсветка работает по конкретным символам, поэтому одинаковые
суммы в разных частях документа не перепутаются. Старые JSON схемы `1.0` нужно
создать заново запуском конвертации.

## Особенности распознавания

- `--ocr auto` (по умолчанию): встроенный текст PDF читается напрямую,
  страницы-сканы распознаются. В смешанных PDF дополнительно распознаются
  области изображений, совпадения с уже извлечённым текстом отбрасываются.
  В режиме `--psm auto` дополнительный проход Tesseract для разрозненного текста
  восстанавливает пропущенные подписи и отдельные строки вне таблиц;
  пересекающиеся с уже найденными словами области повторно не добавляются.
- `--ocr always`: распознать визуальное отображение целиком, например при
  повреждённом текстовом слое PDF.
- `--ocr never`: работать только с существующим текстовым слоем.
- `--psm auto` выбирает режим OCR по наличию таблицы; для ручного выбора
  поддерживаются `--psm 3`, `6`, `11` и другие режимы из справки `--help`.
- Таблицы с видимыми линиями преобразуются в Markdown-таблицы. Для сканов
  ячейки распознаются отдельно: это снижает смешивание соседних столбцов.
  Границы таблицы удаляются до распознавания ячеек; мелкие символы увеличиваются
  с обратным пересчётом координат. Изолированные точки сканирования удаляются,
  а запятые, десятичные точки и минусы сохраняются. У незамкнутых краёв таблицы
  объединение ячеек восстанавливается по фактическим разделительным линиям.
  Объединённые ячейки кладутся в верхнюю левую позицию; Markdown не поддерживает
  rowspan/colspan. Геометрия ячеек используется внутри конвертера и не экспортируется.
- `--no-cell-ocr` ускоряет сканы ценой качества мелких таблиц;
  `--no-tables` отключает восстановление таблиц.
- XLSX отображается через офисный движок, который пересчитывает формулы:
  итог зарплаты не зависит от старого кэша. Пересчёт принудительный, в контейнере,
  с проверкой ошибок и сохранения кэша. LibreOffice использует SinglePageSheets.
- Произвольные таблицы без линий и сложные многоколоночные страницы могут
  потребовать дополнительного layout-анализа; скрипт не гарантирует их
  семантическое восстановление. Символьные координаты сохраняются независимо.
- Отсутствующие шрифты, скрытое содержимое, обрезанный текст в исходных ячейках,
  поля Word и внешний контент зависят от офисного движка. Проверять нужно
  предоставленное отображение. Содержимое вложенных изображений в Office-файлах
  также попадает в обработку смешанного PDF.
- Ошибки OCR в мелких заголовках возможны. В JSON сохраняются предупреждения
  о словах с confidence ниже 0.60; сами оценки в записи символов не дублируются.
- Для TXT/MD задаются UTF-8 и Unicode-шрифт; при необходимости используйте
  `--encoding cp1251` или `--font PATH.ttf`. MD читается как исходный текст.

## Проверка

Из корня репозитория в Linux с установленным Tesseract:

```bash
python -m pip install -e './server[dev]'
python -m pytest server/tests office_sandbox/tests -q
```

Тесты проверяют повторяющиеся суммы, экранирование и Unicode-смещения,
координаты PDF с CropBox и четырьмя поворотами, реальные OCR-координаты цифр,
смешанный PDF, подсветку и отказ использовать изменённый Markdown.
Дополнительно проверяются обязательный полный пересчёт вместо использования
кэша, отбрасывание активного содержимого, безопасное получение результата,
параллельные задания, ожидание свободного слота и отказ работать без песочницы.

Интеграционные тесты требуют доступного Office-сервиса. Один из них создаёт
XLSX с ручным режимом расчёта и **заведомо неправильным кэшем `0`**, а затем проверяет,
что в сохранённой книге и Markdown появился результат `150`, исходник не изменён,
а привязки текста сохранены:

Полный запуск с PostgreSQL, Redis и Office в Compose описан в
[CI workflow](../.github/workflows/tests.yaml). Там используется
`OCR_SANDBOX_TESTS=1` и два воркера каждой стадии; отдельный интеграционный тест
отправляет несколько XLSX одновременно и проверяет результаты формул каждой книги.
Без этой переменной Office-интеграция пропускается. Проверка завершения обработки
и координат не гарантирует отсутствие ошибок распознавания в любом новом документе.
Артефакты и локальные инструменты исключены из git через `.gitignore`.

## Использованные компоненты

- [PyMuPDF: извлечение текста, координаты и таблицы](https://pymupdf.readthedocs.io/en/latest/page.html)
- [Tesseract: TSV и символьные боксы](https://tesseract-ocr.github.io/tessdoc/Command-Line-Usage.html)
- [LibreOffice: параметры экспорта PDF](https://help.libreoffice.org/latest/en-US/text/shared/guide/pdf_params.html)
- [LibreOffice: полный пересчёт calculateAll](https://api.libreoffice.org/docs/idl/ref/interfacecom_1_1sun_1_1star_1_1sheet_1_1XCalculatable.html)
- [Docker: параметры изоляции контейнера](https://docs.docker.com/reference/cli/docker/container/run/)

Docling не требуется: для этого скрипта выбран небольшой набор компонентов
с прямым доступом к координатам слов и символов. Дальнейшая интеграция Docling
для layout-анализа может использовать тот же JSON-контракт.
